# 0003 — Local ComfyUI for dev image generation

**Status:** Accepted (re-evaluate for Phase 3 per-question images)
**Date:** 2026-05-24

## Context

The site needs visual assets — a gallery background, five wizard portraits,
a verdict seal, favicons — generated by an SDXL/FLUX-class image model.
Options:

| Option | Notes |
|---|---|
| **A pre-existing shared RunPod endpoint** | The first thing we tried (`redacted-endpoint-id`). Catastrophic mismatch: the endpoint is character/portrait-bias-loaded for a sibling project's specific use case and ignored our composition/style prompts entirely — returned a photo of an old man and a child when asked for a cosmic void. Also both its workers were rate-throttled, jobs queued indefinitely. |
| **A new RunPod endpoint, configured fresh** | Would work but requires ~15min setup in the RunPod dashboard, pay-per-call, and we'd be paying for cold starts on every iteration. |
| **Cloudflare Workers AI (FLUX-schnell)** | Same vendor as everything else; free tier covers low volume. Needs a CF API token with `Workers AI:Read` scope, which our existing tokens don't have. |
| **Local ComfyUI on the maintainer's workstation** | `<your ComfyUI checkout>` already exists with Juggernaut-XL-v9, RealVisXL_V4, epiCRealism_XL, illustroV3, and other SDXL checkpoints. RTX 4070 produces SDXL images in ~10-15s. |

## Decision

For **one-off content generation** (the gallery background, the 5 portraits,
the verdict seal, the favicons), use **local ComfyUI** at `<your ComfyUI checkout>`
with the Juggernaut-XL-v9 checkpoint.

The pipeline:
1. Start ComfyUI with `--lowvram` (avoids a cold-start `BrokenPipeError`).
2. `scripts/generate-assets.ts` POSTs the txt2img workflow JSON to ComfyUI's
   `/prompt` endpoint, polls `/history/<id>`, downloads the result, runs it
   through `sharp` to convert to WebP at the target dimensions, writes to
   `public/`.
3. Prompts live in `scripts/prompts/<slug>.txt` (positive + `###` separator +
   negative).
4. Results are committed to the repo. The Worker never invokes ComfyUI.

## Consequences

**+** Free, instant iteration. No tokens, no cold starts after the first one,
no per-call cost.

**+** Full control over which checkpoint loads — we can switch between
Juggernaut, RealVis, illustroV3, etc. per-asset if a style needs it.

**+** No new dependency for production — the Worker never touches an
image-gen service. If the maintainer's machine is off, the deployed site is unaffected.

**+** Reproducible from the repo + a copy of the checkpoint: anyone with the
repo + ComfyUI + the same SDXL model can re-derive every asset.

**-** the maintainer's machine has to be on to regenerate. Acceptable: regeneration is
infrequent (when prompts change, when we want a new wizard) and never on the
critical path of a user request.

**-** Occasional flakiness — ComfyUI sometimes hits a `BrokenPipeError` on the
first generation after a cold start. Mitigation: always launch with
`--lowvram`, restart if it errors. Documented in [runbook.md](../runbook.md).

**-** Locks the *art direction* to whatever SDXL can do well. Specifically, we
designed each wizard for a "different art tradition" (engraving for Vexil,
illuminated manuscript for Lorekeeper) and SDXL landed all five as generic
oil paintings instead. We accepted painted-all-five rather than fight SDXL
for traditions it can't reliably do.

## Re-evaluate for Phase 3

This decision is scoped to **dev-time, one-off content generation**. For Phase 3
(generating a unique image per council, on every visitor request), local
ComfyUI would be the wrong tool: it'd require the maintainer's machine to be on 24/7,
public-internet-reachable, and able to handle concurrent requests.

When Phase 3 ships, that's a separate decision. Likely candidates:
- A fresh RunPod endpoint (not the sibling project's) configured for general-purpose
  txt2img with FLUX or similar
- Cloudflare Workers AI's `@cf/black-forest-labs/flux-1-schnell` (needs a CF
  AI-scoped token; same pattern as the Access token we already minted)

Neither matters until Phase 2 ships and we have shareable councils that
benefit from a per-council OG card image.
